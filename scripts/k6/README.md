# k6 WebSocket 부하 테스트 — 채팅방 동시접속자 시뮬레이션

이슈: 동시 접속자가 많을 때 단일 서버가 안정적으로 동작하는지 검증하고, 병목 지점을 실측으로 찾는다.

## 1. 시나리오

- `seed.sql`로 유저 50명 / 방 10개(방마다 5명, 겹치지 않게 전원 배정)를 만든다. 재실행 가능 — 실행 전 `k6user*`/`k6-room-*` 관련 레코드를 의존성 역순으로 먼저 정리한다.
- **`db-tuning/01_seed.sql`과 같이 쓸 때 실행 순서 주의**: `db-tuning/01_seed.sql`은 `email LIKE '%@seed.com'`으로 `base_user_id`(=`MIN(id)`)를 계산하는데, 이 패턴이 `k6user*@seed.com`도 포함한다. k6 시드가 이미 존재하는 상태에서 `db-tuning/01_seed.sql`을 실행하면 `base_user_id`가 틀어져 `seed-room-*` 멤버 배정이 꼬일 수 있다(실측 확인 — k6user가 엉뚱하게 `seed-room-*`의 멤버로 잡혔었음). 두 시드를 같이 쓸 땐 `db-tuning/01_seed.sql`을 먼저 실행하고 `k6/seed.sql`을 나중에 실행할 것.
- k6 VU 50개 = 유저 50명. 각 VU는 로그인 후 자신이 속한 방을 STOMP로 구독한다.
- 방마다 1명(그 방 멤버 중 email 사전순으로 가장 앞선 사람)만 **발신자**로 동작해 일정 간격으로 메시지를 전송하고, 나머지 4명은 **수신만** 하며 대기한다.
- 세션 유지시간은 30초 + `WARMUP_SEC`. 발신 간격(`SEND_INTERVAL_SEC`)을 좁혀가며 부하를 단계적으로 올린다.

```bash
docker exec -i talkie-mysql-1 mysql -uroot -proot talkie < seed.sql
k6 run chat_load_test.js                       # 기본 3초 간격
k6 run -e SEND_INTERVAL_SEC=1 chat_load_test.js # 부하를 올릴 때
```

측정 지표: 메시지 지연시간(SEND→브로드캐스트 수신, p95), 발신/수신 TPS, 연결/구독/발신 성공률, 기대 대비 실제 수신량(무유실 판정).

### 구독 완료 대기 (barrier)와 무유실 판정 방법

Spring의 STOMP 서버(`SimpleBrokerMessageHandler`, `@MessageMapping` 핸들러)는 STOMP `receipt` 헤더를 자동으로 응답해주지 않는다(소스 확인 — SUBSCRIBE/SEND 어느 쪽도 RECEIPT 프레임을 만들어 보내는 코드가 없다). 그래서 이 스크립트는 receipt 대신 다음 방식으로 근사한다:

- **구독 확인**: SUBSCRIBE 전송 시점을 "구독 요청 완료"로 간주한다(SimpleBroker가 SUBSCRIBE를 동기 처리하므로 실질적으로 안전한 근사).
- **발신 시작 지연(warm-up)**: 발신자는 자신의 SUBSCRIBE 전송 직후 `WARMUP_SEC`(기본 3초)만큼 대기한 뒤 첫 메시지를 보낸다. k6는 VU마다 격리된 프로세스라 발신자가 나머지 4명의 구독 완료를 직접 확인할 수는 없으므로(진짜 barrier는 Redis 등 외부 조율이 필요), 고정 지연으로 근사한다. 이 여유가 없으면 "아직 구독 전인 수신자"가 초반 메시지를 못 받는 게 테스트 타이밍 문제인데도 서버 유실처럼 잡힌다.
- **SEND 성공/실패 판정**: 서버는 SEND에도 응답을 보내지 않는 fire-and-forget이라, 발신자 자신도 같은 방의 구독자라는 점을 이용해 "자기 메시지가 브로드캐스트로 되돌아오는 MESSAGE(에코)" 또는 "ERROR"로 성공/실패를 판정한다. 5초 안에 둘 다 안 오면 실패로 확정한다.
- **무유실 판정**: `chat_messages_expected`(발신 횟수 × 방 인원, 발신자 자신도 `/sub/rooms/{roomId}` 구독자라 자기 메시지의 에코를 돌려받는다 — 스모크 테스트로 실측 확인: 발신 290건일 때 무유실이면 수신 1450건=290×5) 총합과 `chat_messages_received` 총합을 비교한다. 실행 종료 후 k6 요약 출력에서 두 카운터의 `count` 값을 직접 대조하거나, `k6 run --summary-export=result.json`으로 저장해 `result.json`의 `metrics.chat_messages_expected.values.count`와 `metrics.chat_messages_received.values.count`를 비교한다.
  - 방마다 측정 구간(30s+`WARMUP_SEC`) 종료 시점에 걸쳐 있던 마지막 SEND 1~2건은, 서버가 정상 처리했더라도 발신자 소켓이 그 에코를 받기 전에 닫혀 카운트에서 누락될 수 있다(스모크 테스트 실측: 발신 292건, 기대 1460 vs 실제 1450, 서버 로그엔 에러 0건 — 방 10개 기준 최대 10건 차이는 이 경계 케이스로 설명됨). 방 개수 × 1~2건을 넘는 차이가 나야 실제 유실로 의심한다.

### 오류율(Rate) 메트릭 기록 방식

`chat_send_success_rate` / `chat_ws_connect_success_rate` / `chat_subscribe_success_rate`는 성공 시 `add(true)`, 실패 시 `add(false)`를 **매 시도마다** 기록한다. (이전 버전은 오류가 발생할 때만 `add(1)`을 호출해서, 표본이 하나라도 있으면 전부 오류였다는 뜻이 되고 오류가 없으면 표본 자체가 비어 threshold가 사실상 평가되지 않는 결함이 있었다.) threshold도 `rate<0.01`(오류율)이 아니라 `rate>0.99`(성공률)로 정의되어 있다.

## 2. 시딩 과정에서 발견한 버그

최초 배정 공식은 `db-tuning/01_seed.sql`의 `(r + n) % 50` 방식을 그대로 가져왔는데, 방 개수가 10개뿐이라 `r`(1~10)과 `n`(0~4)의 합이 최대 14에 그쳐 유저 50명 중 35명이 어떤 방에도 배정되지 않는 결함이 있었다. `(r-1)*5 + n`으로 바꿔, 유저 수(50)와 방×정원(10×5=50)이 정확히 맞아떨어지도록 전원을 겹치지 않게 배정했다.

## 3. k6 스크립트 작성 중 발견한 버그

`data.users.indexOf(vuUser)`로 "이 VU가 방에서 몇 번째 유저인지" 판별하려 했으나 항상 `-1`을 반환해, 어떤 VU도 발신자로 판별되지 않는 문제가 있었다. 원인은 k6가 `setup()`의 리턴값을 **VU/iteration마다 JSON으로 직렬화-역직렬화해서 전달**하기 때문에, 배열 원본과 이후 꺼낸 값이 항상 다른 객체 인스턴스가 되어 참조 비교(`===`, `indexOf`)가 성립하지 않는 것이었다(실측으로 확인: `dbg_idx2` 항상 `-1`). email처럼 값으로 비교 가능한 필드 기준으로 바꿔 해결했다.

또한 이 k6 버전(v1.5.0)의 `k6/ws` 모듈은 `socket.clearInterval`을 지원하지 않는다(호출 시 `TypeError`로 세션이 조용히 끊김, 실측 확인). `setInterval` 핸들을 직접 해제하는 대신 플래그 변수로 반복 내부에서 스스로 멈추는 방식으로 대체했다.

## 5. 근본 원인: STOMP 컨트롤러가 읽음 처리용 스레드풀을 침범해서 실행되고 있었다

0.02s 부하에서 수신 배율이 무너지는 걸 다시 들여다보던 중, 클라이언트 콘솔 로그가 잘려서 "메시지 ID가 #4441까지는 멀쩡히 오다가 갑자기 끊긴다"는 관찰이 나왔다. 이 지점이 이상해서 파일 로깅(`application-local.yml`의 `logging.file.name`)을 켜고 재현 가능한 전체 로그를 확보해 재조사했다.

**계측 결과**: `StompChannelInterceptor.preSend()`에서 SEND 프레임 진입 수를 세보니 k6 발신량과 100% 일치했다. 즉 OS 소켓~STOMP 디코딩까지는 유실이 전혀 없었다. 그런데 `ChatController.sendMessage()` 진입 수를 같은 방식으로 세보니 발신량의 37~50%밖에 되지 않았다 — **컨트롤러 진입 단계에서 이미 절반 이상이 사라지고 있었다.**

스레드 이름을 추적한 결과, `@MessageMapping`이 붙은 `ChatController.sendMessage()`가 `@Async`도 아닌데 `AsyncConfig`가 만든 **읽음 처리 전용 스레드풀**(`core=2, max=4, queue=200`)에서 실행되고 있었다. 원인은 다음과 같다:

- `AsyncConfig`가 읽음 처리용 executor를 `@Bean`으로 컨테이너에 등록하고 있었는데, Spring의 `AbstractMessageBrokerConfiguration`이 STOMP `clientInboundChannel`의 executor를 만드는 과정에서 이 빈과 **같은 인스턴스를 재사용**해버렸다 (`WebSocketConfig`에서 `registration.taskExecutor()`로 새 `ThreadPoolTaskExecutor`를 명시적으로 넘겨줬음에도 무시됨).
- 실증: 읽음 처리 executor 빈의 이름/스레드prefix를 바꿔도 컨트롤러는 여전히 그 executor를 탔다. 반대로 그 빈을 컨테이너에서 완전히 치우자(= `@Bean` 노출을 없애자) 컨트롤러가 즉시 정상적으로 `WebSocketConfig`가 만든 STOMP 전용 풀(`stomp-inbound-*`)에서 실행됐다.
- 결과적으로 핵심 기능(메시지 발행/브로드캐스트)이 원래 "읽음 처리라는 멱등한 부가 기능을 위해 유실을 허용하도록" 설계된 좁은 큐(용량 200, 스레드 최대 4개)를 침범해서 쓰고 있었다. 부하가 커지면 이 좁은 큐가 먼저 넘쳐서 메시지 발행 자체가 조용히 버려졌다 — 4절의 "브로드캐스트 유실"은 사실 이 좁은 큐의 포화였다.

**수정**: `AsyncConfig`에서 읽음 처리 executor를 `@Bean`으로 노출하는 대신 `AsyncConfigurer.getAsyncExecutor()`를 오버라이드하는 방식으로 바꿔, 컨테이너에 별도 `Executor`/`TaskExecutor` 타입 빈으로 등록되지 않도록 격리했다. 동시에 `WebSocketConfig`에 STOMP inbound/outbound 채널 전용 스레드풀(core=8, max=16)을 명시적으로 배선해, 메시지 발행 경로와 읽음 처리 경로가 완전히 분리된 스레드풀을 쓰도록 고쳤다.

## 6. 결론 (재측정 필요 — 아래 수치는 무유실을 증명하지 못함)

수정 후 0.02s 간격(발신 TPS≈410/s) 부하로 재검증한 결과:

| 지표 | 수정 전 | 수정 후 |
|---|---|---|
| 발신 | 14,990 | 14,982 |
| 수신 | 48,510 (배율 3.2x) | 45,549 (배율 3.0x) |
| 에러율 | 0%(겉으로는 정상) | 0% |
| p95 지연 | 178ms (겉수치, 실제로는 발행 자체가 유실) | 1.01s |
| STOMP inbound 풀 상태 | 읽음 처리 풀(core=2/max=4)과 공유되어 포화 | 전용 풀(pool size=16)에서 큐 대기 없이 처리 |

- **이 표의 "수정 후" 수치를 근거로 "유실 없음"이라고 결론 내렸던 것은 철회한다.** README 정의상 정상 수신 배율은 5.0x인데 실측은 3.0x였고, 이 격차만으로는 (a) 실제 브로드캐스트 유실인지 (b) 발신자가 나머지 4명의 SUBSCRIBE 완료를 기다리지 않고 바로 발신을 시작해 초반 메시지가 아직 구독 전인 수신자에게 전달되지 않은 것뿐인지 구분할 수 없었다. 게다가 당시 `sendErrors`/`wsConnectErrors`는 오류가 발생할 때만 표본을 기록해 "에러율 0%"도 신뢰할 수 없는 값이었다.
- 스크립트를 다음과 같이 고쳤다: ① 오류율(Rate) 메트릭을 시도마다 성공/실패로 기록하도록 수정, ② 발신자가 자신의 SUBSCRIBE 전송 후 `WARMUP_SEC`만큼 대기한 뒤 발신을 시작하도록 barrier(근사)를 추가, ③ 메시지별 기대 수신량(`chat_messages_expected`)을 기록해 실제 수신량과 직접 비교할 수 있게 함. 자세한 방법은 2절 "구독 완료 대기(barrier)와 무유실 판정 방법" 참고.
- **이 표는 재측정 전까지 참고용일 뿐이며, 스레드풀 분리(5절) 자체의 방향성은 유효하지만 "유실 없음"이라는 결론은 위 스크립트 수정 이후 재실행해서 `chat_messages_expected` vs `chat_messages_received`로 다시 검증해야 한다.**
- p95 지연시간(1.01s)은 여전히 목표치(1s) 근처라 개선 여지가 있다 — 이는 스레드풀 버그와는 별개의 성능 튜닝 이슈로 남긴다.
- HikariCP 커넥션풀 확장(5절 구버전 내용)은 이 문제와 무관했다 — 커넥션풀이 아니라 애초에 컨트롤러가 요청을 제대로 받지도 못하고 있었기 때문이다.
